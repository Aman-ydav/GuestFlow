# GuestFlow — Design Decisions & Complexity Notes

Filled progressively during the build — this is what interview 1 leans on. Every entry answers "why this, not the alternative?"

## Architecture

- **Folder structure — feature-based, not type-based.** `features/registration|approval|invites|admin` each own their slice + components; shared code lives in `components/`, `lib/`, `services/`, `hooks/`. Chosen so a whole flow (state + UI + tests) can be found, reviewed, or deleted as one unit — a type-based split (`reducers/`, `components/`) scatters one feature across the codebase as it grows.
- **Routing — two route trees, one AppShell.** `/` is the public marketing site (`MarketingLayout`), `/app/*` is the actual product (`AppShell`, role-gated nav). Kept as one route array (`core/routes.jsx`) rather than two separate router instances so there's a single source of truth for the whole site map, and so tests can mount either half via `createMemoryRouter` without duplicating route definitions. `router.jsx` (the real `createBrowserRouter`) is deliberately a thin wrapper around `routes.jsx` — the split exists *specifically* because `createBrowserRouter` is a module-level singleton that doesn't respond to test-driven `window.history` changes; tests need a fresh router per case (`createMemoryRouter`), the app needs exactly one browser-backed router for its whole lifetime.
- **Role switching without real auth — an explicit, labelled demo affordance.** `ui.role` in Redux, no backend check behind it. Chosen because building real auth (JWT, sessions) is out of scope for a frontend case study and would eat the time budget the rubric actually grades; the switcher is clearly labelled "(demo only)" so it's never mistaken for a security boundary. The `services/` boundary means swapping in real auth later touches only `services/`, not every component.

## State management

- **Redux Toolkit**, not Context/useReducer or Zustand. Chosen because four distinct roles (visitor, host, front-desk, admin) all read and write overlapping visitor/invite data from different screens — Context would re-render every consumer on every change; Zustand would work but RTK's `createEntityAdapter` + `createSelector` + devtools + the explicit action-log (every state change is a named, inspectable action) matches "the CV lists Redux Toolkit, be able to defend it in depth" directly.
- **Status transitions are a table, not scattered `if`s.** `lib/statusTransitions.js` exports one `canTransition(from, to)` function consumed by every slice and every mock service call. An invalid move (check-out before check-in, approving an expired invite) is rejected in exactly one place — not re-implemented per screen, and not preventable only by UI discipline (disabling a button doesn't stop a second tab, a race, or a bug elsewhere from calling the action anyway; the table stops it at the data layer regardless of how the call arrives).
- **Normalised state via `createEntityAdapter`** (`{ ids, entities }`) for visitors/hosts/invites — O(1) lookup/update by id instead of `array.find` (O(n)) on every render of the guest-details panel.

## Data layer

- **Mock shape mirrors a real backend 1:1** (see `01-architecture-and-data.md`) — `Visitor`/`Host`/`Invite`/`ApprovalEvent` — specifically so nothing about the Redux slices, selectors, or components would need to change if a real API replaced the mock tomorrow.
- **The abstraction boundary is `services/*Service.js`**, gated by one env var (`VITE_USE_MOCK_API`). Every service function has the identical signature and return shape in both modes; Redux thunks call the service and never know which mode is active.
- **Simulated latency (200–700ms) + ~8% random write failures** (`mocks/mockApiStore.js`) — deliberately, so the loading/error UI (skeletons, disabled buttons, error toasts) has something real to exercise instead of resolving instantly and looking untested.
- **Mock dataset was designed to default to ~3,000 visitors / 400 invites / 24 hosts**, generated, not hand-written — small mock data would hide exactly the problems the "Performance" rubric criterion is checking for (unmemoised filters, missing virtualization). **Temporarily turned down for faster manual QA while the app is still being iterated on (2026-09-22, revised down twice the same day — currently 4 hosts / 7 visitors / 5 invites, check `mocks/generators/seedDataset.js` for the live numbers)** — the complexity analysis below (all the "~3,000 rows" references) describes the algorithm's behavior at that intended scale, which doesn't change with N; only the actual amount of data to click through during testing does. **Restore the large defaults in `mocks/generators/seedDataset.js` before final submission.**

## Complexity analysis (per feature)

| Operation | Data structure | Time | Space | Notes |
|---|---|---|---|---|
| Search visitors by name/email/phone | `useDebounce` (300ms) → local `visitors` array, one combined predicate | O(n) per settled query, not per keystroke | O(k) for k matches | `VisitorFilters` debounces only the text box; status/date filters (discrete) apply immediately without waiting |
| Filter by date / status | Same predicate/pass as search (`selectVisibleVisitors`) | O(n) | O(k) | One combined pass, not three chained `.filter()` calls |
| Render the front-desk table at ~3,000 rows | `VisitorTable` slices the filtered array to one page (15 rows) before mapping to JSX | **O(page size)**, not O(n) | O(page size) | Pagination, not virtualization — a deliberate, documented tradeoff (see below); DOM node count stays flat regardless of dataset size |
| Lookup visitor by id (guest details panel) | `entityAdapter` `entities` map | O(1) | O(1) | vs O(n) `array.find` on a plain array |
| Lookup host by id (table rows, guest panel) | `hostSelectors.selectEntities` map | O(1) | O(1) | Same pattern as visitors — every foreign-key lookup in the app goes through an entity map, never a `.find()` |
| Check pre-approval limit per employee per day | `Array.filter` over today's invites for one host, in `inviteService.createInvite` | O(m) where m = that host's invites that day (small, bounded) | O(1) extra | Documented as the one place this could become an O(1) `countByHostDay` map if profiling ever showed m matters — see `05-state-management-redux.md` |
| Expire unused pre-approvals | Derived on read: `now > windowEnd && status === 'invited'` | O(1) per invite checked | O(1) | No polling/timer needed; always correct whether or not a sweep ran |
| Overstay detection (`getDisplayStatus`) | Derived on read from `checkedInAt` vs `config.overstayMinutes`, same pattern as invite expiry | O(1) per visitor checked | O(1) | Computed at render time in the table/sheet — never stored as a status, so it can't drift out of sync with the clock |
| Approve / reject / check-in / check-out | `canTransition` table lookup + entity `upsertOne` | O(1) | O(1) | Table lookup, not a chain of `if` statements |
| Recent activity for a host (audit trail) | `db.auditEvents.filter` joined against `db.visitors` by `hostId`, sorted, sliced to 20 | O(a + n) where a = total audit events, n = visitors (one join pass) | O(a) | `listAuditEventsForHost` — the one query that isn't O(1)/O(log n); acceptable at this scale, flagged here rather than hidden |

## UX / error handling decisions

- **Feedback is action-specific, not one style everywhere:** form submission → toast (`sonner`) + the page's own success state (Kiosk shows a confirmation screen, not just a toast that scrolls away); field errors → inline, under the field, only after `touched`; invalid backend operation → toast with the service's human-readable message (e.g. "Daily pre-approval limit (5) reached for this host"), not a raw status code.
- **Every mutating button disables itself while its thunk is in flight** (`visitorsSlice.mutatingIds`) — prevents double-submit racing the ~8% simulated failure rate into a confusing double-toast.
- **The photo-capture camera never opens automatically.** It only requests permission after an explicit "Start Camera" click — a deliberate reversal of the first draft (which auto-started on mount). Requesting a browser permission without a clear, user-initiated trigger is exactly the pattern browsers themselves warn against; it also means opening the Kiosk tab doesn't itself trigger a permission prompt. The denied/unsupported path is still a first-class UI state, not a crash, with a working file-upload fallback either way — covered by tests specifically because jsdom has no `navigator.mediaDevices` and would otherwise mask this exact path.
- **Every "not yet loaded" screen has an honest, specific empty state** — "pick a host from the top bar" (no host chosen), "no invites yet — create one" (host has none), "no visitors match these filters" (search too narrow), never a blank screen or a spinner that never resolves.
- **A "current host" concept** (`ui.currentHostId`, picked via a second select next to the role switcher) makes Host Inbox and Invites feel personal — "my pending requests," "my invites" — rather than one shared global queue, matching how the actual requirements describe a host acting on their own visitor requests.

## Testing & verification (what actually proved this works)

- **Vitest + jsdom**, not a real browser — this sandbox's network blocks large binary downloads (Playwright's Chromium fetch timed out after multiple retries against `cdn.playwright.dev`; regular `npm install` traffic is unaffected, so it's specifically the ~150MB browser binary that's blocked, not general network access). Playwright is still installed as a devDependency for real e2e runs on an unrestricted machine later. **Aman has since confirmed the build in a real browser himself**, so this is no longer the only verification — but the automated suite still matters for regressions.
- 22 tests across reducer/transition-table unit tests (cheapest, highest-value per the interview-prep testing notes) and a full-app smoke suite (`createMemoryRouter` + real Redux store + Testing Library) covering: landing page + flow cards, dashboard redirect, kiosk form validation + explicit-click camera flow + upload fallback, no-theme-toggle assertion, sidebar collapse, 404, and — once built — Host Inbox's "pick a host" state, Invites' creation form, and Front Desk's paginated table with a real "no results" filter test.
- Real bugs caught this way, not by inspection: shadcn's `CardTitle` rendered a plain `<div>` (invisible to heading navigation) — fixed at the source since every card title needs it; the initial `shadcn add --all` pulled a broken `import { cn } from "cn"` and a Next.js-only `next-themes` import into every generated file; removing the dark-mode toggle without removing `@custom-variant dark` would have let a visitor's OS-level dark-mode preference silently reskin the whole app with no way to undo it — caught by re-reading `index.css` after the redesign, not by a test (worth flagging: this class of "silent behavior nobody asked for" bug is exactly what a real browser check should hunt for that jsdom can't).

## Tradeoffs & what I'd do with more time

- All four flows are built end-to-end. Code-splitting (`React.lazy` per route) isn't in yet — the build warns about one ~700KB bundle now that all flows are loaded eagerly. Straightforward to add: the route boundaries in `core/routes.jsx` are already the natural split points.
- Front Desk uses **pagination, not virtualization**, at the full ~3,000-row mock scale — a deliberate choice (see the complexity table): simpler, no extra dependency, and DOM cost is already flat at O(page size). Virtualization (`@tanstack/react-virtual`) would be the answer if the dataset were 100k+ or if continuous scroll (not paged) were required by the spec.
- The invite guest-picker (`MultiSelectCombobox`) treats existing mock visitors as a searchable "directory" of people to invite — realistic for a corporate contact-list scenario (matches the original reference screenshot's search pattern), but a real product would also need a path to invite someone with no prior record at all (free-text entry), which isn't built.
- Audit history is per-visitor (`listAuditEvents`) or joined per-host (`listAuditEventsForHost`) on demand — there's no global admin-wide audit log view. Would add a fifth "Audit Log" admin sub-page with more time.
- The route guard is UI-only (sidebar hides links you can't use) — direct URL navigation to any `/app/*` route works regardless of role, same as the role switcher itself: intentionally out of scope, no real auth exists to gate on (see Architecture).
